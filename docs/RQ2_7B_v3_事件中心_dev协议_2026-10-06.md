# RQ2 7B v3：事件中心 dev pilot

状态：在完整 20-pair dev 基线筛查后制定的开发协议；在新的事件中心干预前冻结。它不是事先于 dev 数据的确认性预注册。v2 与 dev_screen 原文件及结果保持原样；40 条 causal-test 不进入本入口。

## 1. 依据与研究对象

dev_screen01 的 2040 条基线标签完整。固定步 2/10/100 的正分数人数分别为 1/4/4，无法满足原 pilot 的 60% 同向门槛。每条轨迹的首次不拒答处，20 个 pair 中 19 个分数大于零；这只是恢复空间，不是干预有效性。

人口规则：固定母清单内全部 20 条 rq2_dev；clean 必须明确拒答，PGD step 0 必须明确拒答。对这些 pair，从 step 1 开始取第一个有效、明确不拒答的 Judge 标签，记为 t*。t* 之前标签缺失则事件未决；不跳过缺失后声称首次。无事件、step 0 不拒答、缺失等分别计数。所有满足事件规则的 pair 进入中心分析，包括 t* 时 StrongREJECT=0 的 pair；不额外筛选正分数或 compliance。

估计对象：已观测首次不拒答事件人口内，同一波形检查点上的干预效应。它不代表所有攻击输入的总体效果。

## 2. 主分析与窗口

主状态固定为 event:first_non_refusal_step:+0。主效用变化为 S_baseline − S_intervention；拒答恢复为 R_intervention − R_baseline；compliance 另报。分数零不等价于明确拒答。

窗口固定为 [-2,-1,0,+1,+3]。中心使用全部事件人口，窗口跨 offsets 比较使用同一事件、同一干预/层的完整配对人口。越界不可截断到边界、不可补为零或删除该 pair 的中心记录。本次中心 20 个，完整窗口 19 个。窗口阶段仅在机制 pilot 合格后单独运行；pilot 的时间差异只作描述，不给出状态依赖因果结论。

事件前后行为差异受到事件定义的选择影响，事件后自然恢复不计作干预成功。所有干预比较使用同一 pair、同一检查点的无干预参考；主门禁不要求每个 offset 都有正向恢复。

## 3. 基线复用与隔离

新配置绑定源 dev_screen 配置 SHA、源 pipeline_state SHA、完整源 artifacts 清单和汇总 SHA；文档和机器协议亦绑定 SHA。源 manifest 必须精确等于冻结母清单中的 20 条 dev；源 resolved manifest 不得含 test。

已有轨迹、回复、标签以只读来源复用，不重跑 2040 条生成/Judge。新阶段的 baseline 使用新 trial ID，同时在 audit 与 baseline_import_map.json 中明确保存源 trial ID、源 run fingerprint、响应 SHA、Judge fingerprint；原记录不改。标签可复用仅限相同模型、生成、Judge 和轨迹参数；这些参数继承源配置且不可在事件配置覆盖。

Oracle 已有的 sham、self_patch、R 零剂量覆盖所有中心 pair×候选层，需与导入参考回复 SHA 一致。缺失或漂移会阻断门禁；不能重选事件或用重新 Judge 的更有利标签替换冻结参考。机制阶段的 sham/reverse_sham 同样审计。此审计不额外生成全轨迹回复。

新输出命名空间 outputs/stage2_rq2/event_dev/<name>，仅接受本 v3 配置。当前入口止于 dev 分析/报告，拒绝 protocol_lock、formal、subspace。源 dev_screen 入口维持只读基线筛查限制。

## 4. 层、剂量与门禁

候选层 [19,24,26,27]；邻层 [18,20,23,25]；远距层 [2,12] 保留为正式设计角色，dev 最小 pilot 不新增远距扫描。主剂量 1.0；0.5 为机制敏感性，1.5 不使用。随机对照每 pair 内先平均，3 次重复不增加样本数。

Oracle：仅在 t* 运行 full_state、self_patch、sham、R 零剂量；邻层运行 full_state。至少 16 个有效事件 dev pair；均值效应至少 0.05；同向比例 ≥0.60；同一 t* 的相邻层也需至少 16 个有效 pair、正均值、≥0.60 同向比例。不得用窗口其他状态替代这个支持条件。参考重放审计必须通过。

机制：Oracle 合格后，在 t* 运行 R 方向、H/随机/sham 对照、0.5 敏感性；clean 反向干预每 pair 仅执行一次对应层/剂量组合。门槛至少 16、均值效应 ≥0.03、同向 ≥0.60，加同事件相邻层支持、二值拒答正向证据、同层 H/随机/sham 对比及 5% 范数审计。缺失标签保留在审计中，额外报告固定事件人口分母的同向比例；缺失不能帮助通过门禁。

所有 pilot 结果只决定是否值得准备独立 formal；不输出机制、双向或状态依赖的确认性结论。Oracle 弱则停止；Oracle 强而 R 弱则保存结果并要求新的 calibration/subspace 协议，当前 run 不自动转入 subspace。

## 5. 窗口与独立 formal 边界

机制合格后可运行预定窗口的候选层 R 主剂量和 sham，报告共同有效 pair 的各 offset 效应、pair-bootstrap CI 和预先规定的 post(0,+1,+3) − pre(-2,-1) 差异。无事件/窗口不足/干预标签不足分别报告；不产生 formal p 值或 FDR 结论。

独立 formal 在锁定层、操作、事件定义、对照与检验家族后才可以打开 40 个 causal-test。每个主比较及必要对照须至少 20 个有效事件 pair；40 个总 pair 不自动满足这个条件。F1 为事件中心效用、F2 为中心二值拒答、F3 为同层机制特异对照、F4 为 clean 反向检验，分别 BH-FDR；窗口为独立预定家族。同一事件内共同人口比较 offsets，随机重复先 pair 内平均。正式结论仍按效用下降→拒答恢复→机制特异→双向→状态依赖逐级建立。

当前交付实现 dev 入口和上述统计约束的机器记录；正式执行器不借用 v2 固定步 formal，也不会由 dev 自动启动。dev 合格后建立独立 formal 配置、锁文件和事件主分析执行器，才构成下一阶段。

## 6. 运行顺序

用 experiments/rq2_event_pilot.py prepare 创建新配置与机器协议。plan、validate 和 run --through state_index 仅 CPU；后者派生事件和人口审计。

用户启动 GPU 时先 run --through identity；通过后 run --from oracle_generate --through oracle_analyze。Oracle 合格再运行 mechanism_generate 到 mechanism_analyze；机制合格才运行 window_generate 到 window_analyze。每次分析会更新 dev 报告。run --stage report 可在 Oracle 分析后独立刷新报告。

验证限于有意义的 CPU 回归、人口/来源检查和必要的真实 identity。不自动运行 GPU、API、全套历史测试。
